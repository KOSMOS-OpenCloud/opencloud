## [ ] NATS Connection Leak — Root Cause offen

Der Cooldown verhindert die Eskalation, aber die Ursache fuer den
**initialen** Connect-Fehler ist nicht abschliessend geklaert.

### Beobachteter Ablauf (2026-09-18 20:07-20:08)

```
20:07:50.364  container stop  (Tag 1729, 21 Min gelaufen, NATS gesund)
20:07:50.400  container died
20:07:50.436  container remove
20:07:50.609  container create (Tag 1756)
20:07:50.667  container start
20:07:50     NATS-Server ready, JetStream ready, nats ping OK
20:08:21     storePP: "Failed to connect to NATS Server: cannot assign requested address"
             → ab hier Eskalation: jedes unacked Event triggert neuen Connect-Versuch
```

Container-Wechsel per `nu compose --auto-apply` OHNE Pod-Restart.
Gleicher Pod = gleicher Network-Namespace.

### Fakten

- NATS im neuen Container war nach ~1s ready (jetstream probe OK)
- Der alte Container hatte ~200 TCP Connections (gesund)
- Port-Erschoepfung trat erst 31s nach Start des neuen Containers auf
- Null NATS-Fehler im alten Container waehrend seiner 21 Min Laufzeit
- `NewStore()` ist lazy: `n.conn = nil` bis zum ersten Write
- `store.Create()` + `updateNatsStore()` oeffnet pro Service-Init
  eine eigene kurze NATS-Connection (Connect + defer Close)

### Hypothese

1. Beim Container-Wechsel starten alle OpenCloud-Services gleichzeitig
2. Jeder Service ruft `store.Create()` auf → `updateNatsStore()` oeffnet
   eine NATS-Connection, prueft Bucket-TTL, schliesst sie sofort wieder
3. Der Postprocessing-Store (nats-js-kv) ist lazy, verbindet erst beim
   ersten `storePP()` Aufruf
4. Zwischen NATS-Server-Ready und erstem storePP liegen 31s — genug
   Zeit fuer einen voruebergehenden Connect-Fehler (Timing, Port-Conflict
   durch TIME_WAIT Sockets des alten Containers, oder Race mit anderen
   Service-Inits)
5. **Ein einziger fehlgeschlagener Connect** laesst `n.conn = nil` stehen
6. NATS JetStream liefert sofort alle pending Events (MaxAckPending=10000)
7. Jedes Event → `storePP` → `initConn` → `Init` → `Connect` → neuer
   TCP Socket im Kernel
8. Innerhalb von Sekunden: 28232 Sockets → Ephemeral Ports erschoepft
9. Ab jetzt kann NICHTS mehr verbinden (auch nicht NATS selbst)

### Was noch zu klaeren ist

- [ ] Warum genau scheitert der erste Connect nach 31s?
      Moeglichkeiten: TIME_WAIT Sockets, Race bei updateNatsStore,
      kurzzeitige NATS-Ueberlastung durch parallele Service-Inits
- [ ] Kann man `NewStore` eager statt lazy machen? (`Init()` direkt
      in `NewStore` aufrufen, bevor Events ankommen)
- [ ] Soll `updateNatsStore()` die gleiche Connection wie der Store
      nutzen statt jedes Mal eine eigene zu oeffnen?
- [ ] MaxAckPending=10000 ist sehr hoch — reduzieren auf z.B. 100?
- [ ] Alternative: Pod-Restart statt Container-Wechsel bei Image-Updates
      (vermeidet shared Network-Namespace Probleme)
